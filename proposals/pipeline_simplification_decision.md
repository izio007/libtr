# Утверждённое решение: упрощение работы и отчётности

Статус: утверждено Шефом в текущем обсуждении; не свидетельство завершения реализации.
Область: исполнение, сравнение результатов, артефакты и экономия контекста.
Математические замечания к триангуляционному DOCX этим решением не утверждаются.
Нормативный первоисточник: .clinerules; контракт реализации:
tools/pipeline/engine_contract.md. Очередь реализации: существующая карточка
PIPELINE-ENGINE в need_work.md, без новой параллельной очереди.

## Решение

1. До изменения задать ожидаемый эффект, неизменяемые свойства и критерий
   завершения. Не расширять обязательный объём после локального PASS без основания.
2. Разделять факт исполнения, соответствие требованиям и изменение результата.
   Неизменный результат может быть ошибочным; изменённый — допустимым.
3. Хранить одинаковый расчётный результат один раз, а факт нового исполнения —
   короткой записью с происхождением и ссылкой. PID, время и job id не являются
   расчётными метриками, кроме явно проверяемых характеристик исполнения.
4. Проверять текущие ожидания сразу, включая неизменный результат. Сравнивать
   также наличие метрик, состав checks и их состояния. Не скрывать малые
   численные отличия допуском; допустимость и идентичность различаются.
5. Не генерировать повторные графики и документы при неизменных зависимостях.
   Успешные подробные текстовые логи не создавать. Отказы сохранять по регламенту.
6. Не повторять чтение, сборку или запуск при неизменном препятствии.
   Следующий шаг устраняет причину или получает недостающее свидетельство.
7. В контекст передавать итог, отличия и точный остаток; история и полные
   результаты остаются в файлах. Для завершения использовать один выбранный
   кандидат и заранее определённые обязательные проверки.
8. Сначала подключить существующий механизм к реальным метрикам MATLAB,
   затем устранять дубли артефактов; не создавать новую платформу или БД.

## Граница реализации и проверки

Существующая поддержка общего движка описана в engine_contract.md.
Возврат реальных MATLAB-метрик и устранение дублирования старого серверного
исполнителя ещё требуют реализации; утверждение решения не закрывает их.
Адресные проверки реализации должны охватывать: одинаковый результат без новой
копии; изменённые ожидания при прежних числах; исчезнувшую метрику/check;
PASS → NOT_RUN; допустимое и недопустимое изменение; новое происхождение при
тех же числах; изменение оформления без повторного расчёта; Fail-Fast.
Для этой фиксации решения checks: согласованность с существующим контрактом,
отсутствие ложного заявления о реализации, адресный git diff --check.
