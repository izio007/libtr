# Методика тестирования: понятный формат

Методика должна позволять человеку ответить: **какой опыт проводим, что в нём можно изменить и какой результат хотим увидеть**.

Начните с перечня сценариев. Для каждого дайте короткое название и смысл: «обрыв и восстановление», «переход на новую полку», «отказ от помехи». Затем заполните карточку выбранного сценария по [шаблону](testing_methodology_template.md).

## Карточка сценария

В ней нужны четыре части:

1. **Что проверяем.** Одна понятная задача и исходное состояние.
2. **Что подаём.** Последовательность событий по этапам: времена, данные, помехи, пропуски.
3. **Что настраиваем.** Человеческое название настройки, её значение и поле существующей конфигурации.
4. **Что хотим увидеть.** Результат каждого этапа, допустимая ошибка и срок реакции с явным началом отсчёта.

История входа, настройки объекта и критерии оценки различаются. Например, ширина принимаемой окрестности — настройка фильтра; допустимая ошибка выхода — требование к результату. Одно не заменяет другое.

Описание поведения остаётся понятным при замене реализации. Таблица соответствия настройкам позволяет применить его в текущем проекте. Если нужной настройки нет, пишите «не поддерживается», а не придумывайте имя поля.

## Как менять опыт

Меняйте входные события или значения в карточке. Для сравнения двух политик создайте два именованных варианта с общим входом и явно указанными различиями настроек.

Числа конкретного опыта не становятся константами алгоритма. Незаданные значения отмечайте только там, где они действительно нужны для решения, и объясняйте, какой результат без них нельзя оценить.

Указывайте, поддерживает ли исполнитель этот документ непосредственно. Если карточка ещё не подключена, изменение Markdown не считается изменением исполняемого теста.

## Как оценивать результат

До исполнения запишите ожидания по этапам. После исполнения сопоставьте с ними выход, доступность результата и переходы режима. Для каждой строки укажите: соответствует, не соответствует или оценить нельзя с конкретной причиной.

График помогает увидеть всю историю; листинг объясняет переходы. Ни график без критериев, ни перечень статусов без проверки поведения не заменяют оценку.

В конце приведите короткий перечень обязательств и покажите, в каких сценариях они проверяются. Не требуйте от читателя расшифровывать десятки перекрёстных кодов, чтобы понять один опыт.

## Перед передачей на реализацию

Читатель должен видеть выбранный сценарий, редактируемые входы и настройки, ожидания для каждого этапа и ещё не решённые условия. Конфигурация исполнения должна соответствовать карточке; скрытые подстановки параметров запрещены. Ожидания не получают из фактического выхода проверяемой реализации.

Это рабочий формат аналитика. Он не предписывает язык, устройство ядра или средство запуска.
