# Понятная программная логика: проектирование, реализация и проверка

Самостоятельное руководство и контракт для разработчика или программирующего агента. Применимо к обработке данных, вычислительным конвейерам, фоновым задачам, устройствам, интерфейсам и другим процессам, поведение которых зависит от входов и накопленного состояния.

Цель — сделать правило поведения понятным до запуска программы, его реализацию обозримой, а ошибку локализуемой. Для этого отдельно описываются **наблюдаемые факты, условия, события, решение, исполнение и принятие результата**. Такое разделение не требует отдельного класса, потока или сервиса для каждого понятия.

Документ не зависит от других файлов проекта. Полный нейтральный пример с реализацией и тестами приведён в разделе 14. Слово «эталон» означает проверяемый образец организации логики; конкретная предметная политика всегда задаётся требованиями.

Для первого знакомства достаточно разделов 1–3 и примера в разделе 14. Разделы 4–13 раскрывают проектные решения; разделы 16–18 можно использовать как рабочие шаблоны, инструкцию агенту и критерии приёмки. Читать весь файл за один раз не требуется.

**Применение в libtr.** Задача и [.clinerules](../.clinerules) определяют объём работы. [V_PROCESS_CONFIGURATOR.md](V_PROCESS_CONFIGURATOR.md) задаёт применимый состав предметного описания, [PaeroPrincipe.md](PaeroPrincipe.md) — математическое основание и разделение вычислительных обязанностей. Это руководство уточняет данные, состояние и правила решения в затронутой логике; само по себе оно не является заданием на рефакторинг.

Для правил проекта, преобразования представлений и простой упаковки документ не вводит карточки, планы, тесты, журналы или приёмку. Достаточно относящихся к задаче разделов. Описание и примеры хранятся в Markdown.

## 1. Что считать понятной логикой

Для любого наблюдаемого действия разработчик должен ответить на шесть вопросов:

1. Какие входы и ранее сохранённые сведения были доступны?
2. Какие условия по ним вычислены?
3. Какое правило выбрано и почему другие не выбраны?
4. Какие действия разрешены этим правилом?
5. Что фактически произошло при выполнении?
6. Какие данные и состояние приняты после выполнения?

Если ответ требует искать изменение одного флага по десяткам функций, границы ответственности недостаточно ясны. Если для проверки правила выбора приходится запускать всю численную модель или подключать внешний сервис, решение слишком тесно связано с исполнением.

**Главный результат проектирования — явное решение.** Его удобно представить объектом `Decision` или `ActionPlan`: идентификатор правила, разрешённые действия, порядок выполнения, реакции на исходы. Для маленькой задачи достаточно компактной структуры из нескольких полей.

Понятность не определяется количеством `if`, длиной таблицы или числом слоёв. Небольшой `switch` с именованными условиями может быть прозрачным. Большая матрица может скрывать неописанные переходы и противоречивые правила. Выбирается представление, в котором проверяющий видит смысл и границы каждого решения.

## 2. Словарь и границы ответственности

| Понятие | Что означает | Пример |
|---|---|---|
| Вход | То, что пришло извне | Новый пакет, команда остановки, момент времени |
| Метрика | Вычисленная численная характеристика | Количество строк, возраст результата, величина ошибки |
| Предикат | Условие с определённым смыслом | `is_batch_valid`, `is_timeout_reached` |
| Событие | Именованный факт, который рассматривает логика | `BATCH_RECEIVED`, `TIMEOUT`, `RESET_REQUESTED` |
| Разрешающее условие, guard | Дополнительное условие применимости перехода | Запрос на запуск разрешён только при свободном ресурсе |
| Фаза | Режим, определяющий допустимое продолжение процесса | Накопление, обработка, удержание, завершение |
| Контекст | Память конкретного процесса | Фаза, принятый результат, времена и счётчики |
| Правило перехода | Связь состояния, события, условий и реакции | При корректном пакете выбрать построение результата |
| План | Принятое намерение выполнить действия | Построить отчёт; принять при успехе |
| Действие | Конкретная операция | Рассчитать сводку, записать файл, очистить окно |
| Результат действия | Факт исполнения и его данные | Успех с кандидатом результата либо отказ с причиной |
| Фиксация, commit | Принятие разрешённых изменений контекста | Заменить модель успешным кандидатом |
| Инвариант | Свойство, которое должно сохраняться | В фазе готовности существует принятый результат |

Предикат и событие не обязаны иметь взаимно однозначное соответствие. Несколько предикатов могут сформировать одно событие; один действующий предикат может участвовать в нескольких guards. Однако имя не должно обозначать сразу состояние, команду и результат операции.

Общую модель одного шага можно записать так:

$$
\begin{aligned}
(M_k,P_k,H_k^*)&=Observe(I_k,C_k,K),\\
(E_k,Q_k^*)&=Events(P_k,H_k,Q_k,Inbox_k),\\
\Pi_k&=Decide(S_k,P_k,E_k,K),\\
R_k&=Execute(\Pi_k,I_k,C_k),\\
C_{k+1}&=Commit(C_k,H_k^*,Q_k^*,\Pi_k,R_k).
\end{aligned}
$$

Здесь `I` — входной снимок, `C` — контекст, `S` — управляющая фаза внутри него, `K` — конфигурация, `M` — метрики, `P` — признаки, `H*` — кандидат новой памяти наблюдений, `Q*` — кандидат памяти отложенных событий, `E` — события, `Π` — план, `R` — фактическое исполнение. Память `H` и `Q` относится к контексту и нужна только при соответствующем поведении. Фиксация учитывает также судьбу событий из плана и исполнения. Формулы показывают зависимости, а не предписывают пять отдельных подсистем.

## 3. Как получить правила из требований

### 3.1. Начинать с наблюдаемого обещания

Фраза «система должна быть надёжной» не определяет проверяемое поведение. Её нужно раскрыть, например:

> Если построение нового результата завершилось отказом, предыдущий принятый результат сохраняется, а потребитель получает признак отсутствия успешного обновления.

Это обещание определяет входную ситуацию, запрещённое изменение, допустимый выход и проверку. После него уже можно выбирать структуру кода.

Существенное правило должно быть понятно из кода, комментария или предметного описания. В libtr существенные проектные требования выбранного материала имеют один основной текст и постоянный ID по [V_PROCESS_CONFIGURATOR.md](V_PROCESS_CONFIGURATOR.md); в остальных местах ставят ссылки. Краткое техническое пояснение не требует отдельного требования или карточки, а перестройка документа не отменяет прежние идентификаторы. Для записи требования достаточно следующих сведений:

| Поле | Содержание |
|---|---|
| `requirement_id` | Стабильное имя требования |
| Условия | Начальное состояние, вход и необходимые предпосылки |
| Обязательная реакция | Решение, действия и итог |
| Запрет | Что не должно произойти |
| Неуспешный исход | Что делать при недостаточных данных или отказе операции |
| Пример | Один конкретный вход и ожидаемое наблюдаемое поведение |

В одном требовании должна быть одна основная проверяемая идея. Не нужно искусственно дробить каждое слово на отдельный номер.

### 3.2. Различать свойства состояния и перехода

**Инвариант состояния:** `READY` предполагает наличие принятого результата. Его можно проверить на одном снимке контекста.

**Инвариант перехода:** неуспешная попытка обновления не заменяет ранее принятые данные. Для проверки нужны контексты до и после шага.

**Требование прогресса:** если поступают достаточные данные, действие получает ресурс и заканчивается успешно, процесс достигает готовности. Здесь важны предположения об окружении. Нельзя обещать завершение при бесконечном отсутствии данных или постоянно недоступном ресурсе.

Полнота таблицы переходов, сохранение инвариантов и возможность продвижения — разные вопросы. Наличие строки для каждого события не доказывает, что процесс когда-либо выйдет из ожидания.

### 3.3. Связать требование с реализацией и проверкой

Полезна короткая связь:

```text
R_KEEP_PREVIOUS
    → правило retry_or_hold
    → функция commit_result
    → проверка failed_update_preserves_previous_result
```

По ней видно, где правило реализовано и чем проверено. Тест получает ожидаемый смысл из требования. Он не вычисляет ожидание повторным вызовом производственной функции выбора.

## 4. Данные и контекст

### 4.1. Один владелец изменяемого состояния

Контекст принадлежит одному обрабатываемому объекту: заданию, источнику данных, документу или сеансу. Правила могут быть общими и неизменяемыми, память — индивидуальной.

В контексте оставляют только сведения, влияющие на последующие решения или необходимые для выдачи результата. Обычно это фаза, принятые данные, их версия и качество, история нужных детекторов, активная операция. Очереди и таймеры добавляются только при соответствующем поведении.

Для каждого поля нужно знать:

- кто имеет право его менять;
- когда оно появляется и становится недействительным;
- что считается отсутствующим значением;
- какой сброс его очищает;
- можно ли его однозначно вычислить из других полей.

Два независимо изменяемых поля с одним смыслом — например, `state=READY` и `is_ready=true` — создают риск расхождения. Одно значение лучше выводить из другого, если у них действительно одинаковый смысл.

### 4.2. Не смешивать отсутствие, ноль и недостоверность

Нулевое число может быть допустимым результатом. Пустой пакет может быть пришедшим, но непригодным входом. Отсутствие пакета означает, что новой проверки вообще не было.

Полезно различать:

```text
Нет входа
Есть допустимый вход
Есть недопустимый вход с причиной
```

Такое различие особенно существенно для счётчиков ошибок и восстановления. Новое наблюдение, не прошедшее проверку, не обновляет время последних достоверных данных.

### 4.3. Один снимок для одного решения

Все предикаты одного логического шага читают согласованный снимок. Если между проверкой качества и проверкой срока данные меняются, итоговое решение может относиться к комбинации, которой в действительности не существовало.

Снимок не обязательно означает копирование всей памяти. Это может быть неизменяемая структура, согласованное чтение под блокировкой или переданная версия данных. Важно, чтобы смысл наблюдаемой версии был определён.

Изменения сначала представляют кандидатом. Условия и селектор не изменяют исходный контекст. Только назначенный владелец фиксации принимает разрешённые изменения. Такой порядок упрощает повторный вызов проверки и воспроизведение ошибки.

## 5. Как выделять состояния и фазы

### 5.1. Критерий отдельного состояния

Отдельная управляющая фаза нужна, когда она меняет **допустимые будущие реакции**. Она имеет смысл даже между вызовами функций. Полное состояние процесса шире фазы: оно включает принятые данные, память детекторов и другие необходимые сведения.

Диагностический статус последней попытки можно хранить отдельно. Например, отказ расчёта не обязательно закрывает приём новых пакетов: фаза остаётся `OPEN`, а статус попытки становится `FAILED`. Это различие явно показано в разделе 14.

| Наблюдаемое различие | Обычно подходит |
|---|---|
| После завершения новый запуск запрещён до сброса | Отдельная фаза |
| Изменился численный порог | Параметр конфигурации |
| В текущем такте нужно пересчитать результат | Действие или событие расписания |
| Результат имеет низкое качество | Поле качества; отдельная фаза, если меняется режим обработки |
| Объект обслуживается раньше других | Приоритет; отдельная фаза только при ином жизненном поведении |
| Сейчас исполняется строка функции | Обычно не самостоятельная фаза |

Не нужно создавать состояние для каждой функции. Обратная крайность — одна фаза «работает» с десятками скрытых булевых режимов — тоже затрудняет понимание.

### 5.2. Разделять независимые аспекты

Жизненная фаза, качество результата и срок очередного обновления могут существовать одновременно. Их необязательно перемножать в названия наподобие `READY_LOW_QUALITY_WAITING_FOR_TIMER`.

Разделение на поля уменьшает громоздкость, но требует описать допустимые сочетания. Если фаза `READY` разрешает только пригодный результат, комбинация `READY` и `result_missing` является нарушением инварианта. Если допускается старый результат, это должно быть явно выражено состоянием качества.

### 5.3. Паспорт фазы

Это перечень вопросов для описания фазы, а не требование отдельной карточки или файла. Если ответы уже понятны из кода и предметного описания, дублировать их не нужно.

Для каждой используемой фазы определяются:

| Поле | Смысл |
|---|---|
| Назначение | Почему процесс может находиться здесь |
| Вход | По каким правилам сюда переходят |
| Инвариант | Какие данные и ограничения должны сохраняться |
| Разрешённые действия | Что можно выполнять при пребывании |
| Выход | Какие события и guards разрешают смену фазы |
| Отказ | Что сохраняется и куда переходит процесс при неуспехе |
| Сброс | Какие поля очищаются при завершении жизненного цикла |

Действия входа выполняются при реальном входе в фазу, а не при каждом её опросе. Для перехода в ту же фазу нужно определить, считается ли он повторным входом. Иначе счётчик, таймер или накопленный результат может сбрасываться на каждом такте.

## 6. Как писать условия

### 6.1. Именовать смысл, а не синтаксис

Хорошие имена отвечают на вопрос «что установлено»: `has_enough_samples`, `is_context_consistent`, `is_result_current`. Имена `check_3`, `flag2`, `condition_ok` не передают смысла.

Условие выделяется отдельной функцией, когда у него есть самостоятельное предметное значение, входы и границы. Простое объединение нескольких готовых признаков можно записать непосредственно в селекторе. Не требуется создавать функцию-обёртку вокруг каждого технического сравнения.

Предметные пороги и формулы не размещаются в диспетчере. Например:

```text
sample_count = metrics.sample_count
window_ready = has_enough_samples(sample_count, config.minimum)
```

Селектор получает `window_ready`, а не повторяет во многих ветках правило `sample_count >= minimum`.

### 6.2. Контракт предиката

У функции условия определяются входы, единицы при необходимости, граница сравнения, результат при отсутствии данных и допустимые изменения её собственной памяти. Чистый предикат не меняет ничего. Детектор с памятью возвращает кандидат её следующего значения.

Пример границы:

$$
p_{expired}=\mathbf1\{t_{now}-t_{accepted}\ge T_{max}\}.
$$

Здесь равенство уже означает истечение срока. Замена `>=` на `>` меняет требование, даже если большинство обычных примеров продолжает проходить.

### 6.3. Метрика отдельно от решения по ней

Численная функция вычисляет величину; предикат интерпретирует её по требованиям. Это позволяет отдельно проверить формулу и отдельно — правило допуска.

При этом не нужно пересчитывать дорогую метрику для каждого предиката. Она вычисляется один раз для конкретной версии данных и передаётся как значение с признаком доступности. Метрика, зависящая от ещё не выполненного расчёта, не может участвовать в предварительном решении как будто уже известная.

Для недоступной метрики задаётся одно из двух представлений: значение плюс `available`, либо явное состояние `UNKNOWN`. Превращать неизвестность в «проверка пройдена» нельзя. Конкретная реакция на неизвестность — ожидание, отказ или допустимое продолжение — является требованием проекта.

### 6.4. Сложные условия

Сложное правило сначала разбивается на смысловые признаки, затем собирается логическим выражением:

```text
can_build = input_valid AND enough_data AND update_due AND context_valid
```

Для каждого признака понятно, где он вычислен. Если нужно объяснить отказ, возвращается набор причин или первая причина по заданному порядку. Один безымянный `false` может оказаться недостаточным для диагностики, но и отдельная иерархия исключений для каждого сравнения обычно не нужна.

## 7. События, время и накопительная память

### 7.1. Тип события задаёт его жизнь

| Тип | Когда возникает | Что делать, если сейчас не выбран |
|---|---|---|
| Условие уровня | Пока предикат истинен | Пересчитать на следующем шаге |
| Фронт появления | При переходе false → true | Сохранить до обработки или явно разрешить потерю |
| Фронт исчезновения | При переходе true → false | Та же явная политика |
| Внешний запрос | При поступлении сообщения или вызова | Обработать, отложить либо отклонить с результатом |
| Наступление срока | По таймеру или счётчику | Определить перенос, пропуск или выполнение просроченного действия |

Для фронта появления:

$$
e_k=p_k\land\neg p_{k-1}.
$$

Фронт существует только в момент изменения. Если он проиграл приоритетному событию и нигде не сохранён, повторный пересчёт предиката его не восстановит. Для сохранения достаточно записи `pending`; отдельный брокер сообщений из этого не следует.

Отложенное событие проверяется на актуальность перед исполнением. Старый сигнал восстановления не отменяет новую активную ошибку.

### 7.2. Считать именно то, что требуется

Для серии плохих наблюдений разумна такая явно выбранная семантика:

$$
n_k=\begin{cases}
n_{k-1}+1,&\text{получено новое плохое наблюдение},\\
0,&\text{получено новое хорошее наблюдение},\\
n_{k-1},&\text{нового наблюдения нет}.
\end{cases}
$$

Сигнал лимита может проверяться по уже обновлённому `n_k`. Это нужно указать, иначе возможна ошибка на один шаг.

Число плохих наблюдений, число тактов активной ошибки и длительность ошибки в секундах — три разные метрики. Их нельзя заменять друг другом из-за похожего имени счётчика.

### 7.3. Время является входом

Логическая функция получает `now` или уже вычисленную длительность. Она не читает часы в нескольких местах внутри одного решения. В проверках время задаётся напрямую, поэтому ожидание реального таймера не требуется.

Следует различать время возникновения данных, время их получения и время обработки. Для длительностей выбирается согласованный источник времени; переход календарных часов сам по себе не должен становиться предметным таймаутом, если такой эффект не предусмотрен.

У периодического действия описывается один режим:

- выполнить один раз и назначить следующий срок относительно текущего момента;
- сохранить исходную сетку времени и пропустить пропущенные интервалы;
- обработать накопившиеся интервалы с заданным пределом.

Это разные политики. Простая проверка номера такта по модулю подходит лишь при определённых предположениях о непропущенных тактах и периодичности вызова.

### 7.4. Гистерезис и подтверждение

Если показатель колеблется у порога, иногда нужны разные границы входа и выхода либо несколько подтверждений подряд. Такое поведение вводится по наблюдаемой проблеме или требованию. Порог, число подтверждений и реакция на отсутствие данных должны быть явными.

Нельзя незаметно добавить «успокоение» в функцию условия: оно меняет время реакции и требует памяти. Эта память относится к конкретному детектору и сбрасывается по определённому правилу.

### 7.5. Память наблюдений и принятый результат

Увидеть новое наблюдение и принять построенный по нему результат — разные действия. Если расчёт завершился отказом, память детектора всё равно может нуждаться в обновлении: например, чтобы не объявлять один и тот же фронт новым при следующем вызове. Это определяется контрактом конкретного детектора.

Поэтому фиксация не сводится к правилу «при успехе сохранить всё, при отказе не менять ничего». Отдельно задаются принятие истории наблюдений, сохранение или потребление события и замена предметного результата. Изменение этих частей по разным правилам должно быть явным.

## 8. Выбор перехода и разрешение конфликтов

### 8.1. Сначала применимость, затем приоритет

Применимое правило соответствует текущему состоянию и событию, имеет истинный guard и не запрещено действующими ограничениями. Приоритет сравнивается только между применимыми правилами.

Иначе высокий флаг без подходящего перехода может бесконечно блокировать полезное событие ниже по списку. Для неприменимых запросов также задаётся реакция: отложить, отклонить или игнорировать согласно их семантике.

Понятие перехода с событием и guard, а также последовательная обработка логического шага формализованы, например, в SCXML. Здесь эти понятия используются без требования внедрять XML или соответствующий движок.[1]

### 8.2. Выбрать политику совпадений

**Один переход за шаг.** Выбирается применимое правило с наивысшим приоритетом; равенство разрешается стабильным вторичным порядком. Для остальных событий определяется судьба.

**Один переход и несколько совместимых действий.** Выбранное правило может содержать несколько операций. Это не означает, что разрешено объединить все сработавшие переходы.

**Несколько переходов или параллельных областей.** Нужна отдельная семантика: порядок, конфликты записи, условия видимости промежуточных изменений и ограничение числа внутренних шагов. Такой режим вводится только при реальной необходимости.

Для базовой реализации проще определить один согласованный снимок и один итоговый переход. Если после исполнения порождаются внутренние события, явно задаётся, будут ли они обработаны в том же логическом шаге или в следующем. Неограниченный цикл «выполнить — пересчитать события» может не завершиться.

### 8.3. Таблица перехода должна описывать отказ

| Поле | Содержание |
|---|---|
| `rule_id` | Стабильный идентификатор правила |
| `source_state` | Где правило применимо |
| `event`, `guard` | Что произошло и что дополнительно требуется |
| `priority` | Как разрешается конкуренция |
| `actions` | Упорядоченный план |
| `on_success` | Следующая фаза и принимаемые данные |
| `on_not_ready` | Реакция на недостаточность входов, если она возможна |
| `on_failure` | Реакция на неуспешное действие |
| `event_disposition` | Подтвердить, отложить, отклонить или объединить |

Для необработанного события определено поведение по умолчанию. Нулевая ячейка массива не должна случайно становиться переходом в состояние с номером ноль.

### 8.4. Таблица, маска и стоимость

Идентификатор события и маска событий — разные типы. Для `m` независимых булевых признаков существует до `2^m` наборов. Таблица с `m` столбцами может индексироваться одним выбранным `EventId`, но не произвольной маской всех признаков.

Маска действий задаёт выбранное множество. Порядок исполнения всё равно должен быть определён отдельно. Если порядок зависит от номера бита, это часть контракта, а не случайность реализации.

Прямое чтение ячейки может иметь константную стоимость. Это не превращает вычисление всех признаков, обход действий и обработку произвольного числа объектов в константную операцию.

## 9. План действий, исполнитель и фиксация

### 9.1. План можно проверить без тяжёлого вычисления

Если процесс возвращает план, его минимальное содержание — выбранное правило, действия и реакция на исход. Для одного действия достаточно кода события, команды или явного вызова. При сложных зависимостях добавляются требуемые входы, ожидаемые версии, порядок и политика принятия данных.

План не содержит готовый результат ещё не запущенной операции. Он говорит: «нужно построить новый результат и принять его при успехе». Это позволяет проверить намерение независимо от вычислительной функции.

### 9.2. Действие имеет свой контракт

У каждого действия описываются:

- входы и предпосылки;
- возвращаемый кандидат и диагностические сведения;
- возможные статусы;
- разрешённые изменения;
- побочные эффекты и допустимость повторного запуска.

Статусы различаются настолько, насколько различается реакция системы. Если `NOT_READY`, `FAILED` и `SKIPPED` приводят к разным решениям, их нельзя прятать за одним `false`. Если задача различает только успех и ожидаемый отказ, двух исходов достаточно.

Ожидаемый предметный отказ обрабатывается явно. Неожиданная ошибка программы не должна превращаться в тихий успешный переход или бессодержательное «попробуем позже». Перехватывается определённый класс ошибок, а не всё подряд без диагностики.

### 9.3. Зависимые и независимые действия

При отказе операции блокируются действия, которым нужен её новый результат. Журналирование или выдача статуса могут выполняться независимо, если соблюдены их собственные предпосылки.

Для простой выбранной цепочки:

$$
ok_i=\mathbf1\{status_i=OK\},\qquad
chain_{i+1}=chain_i\land ok_i.
$$

Это частный случай. Для ветвящегося плана нужно знать конкретные зависимости. Пропуск действия не означает появления его результата. Если допускается старая принятая версия, это отдельная явно удовлетворяемая зависимость.

Не требуется строить универсальный графовый исполнитель для двух последовательных функций. Достаточно выразить зависимость так, чтобы её видел разработчик и проверял тест.

### 9.4. Успех решения и успех действия различны

Выбор команды построения не означает, что результат уже построен. Фаза, обещающая наличие нового результата, принимается только после нужного успешного исхода.

При этом переход в `RUNNING` до завершения асинхронной операции может быть совершенно правильным: такая фаза означает, что запуск принят, а не что результат готов. Семантика названия определяет допустимый момент перехода.

Политика фиксации отвечает отдельно на вопросы:

1. Принимаются ли хорошие входные данные, если последующий расчёт не удался?
2. Сохраняется ли прежний результат?
3. Какие метаданные становятся неактуальными?
4. Какой статус получает потребитель?
5. Когда запрос считается обработанным?

Локальная фиксация не отменяет уже выполненный внешний эффект. Отправленное сообщение, созданный внешний объект или списание ресурса требуют собственного протокола результата и повторения. Обещание «откатим весь шаг» допустимо только в реально управляемой транзакционной границе.
## 10. Как выглядит понятная реализация

### 10.1. Диспетчер показывает порядок

Хороший диспетчер читается как перечень уже определённых обязанностей:

```text
input_snapshot = normalize(raw_input)
metrics, candidate_memory = measure(input_snapshot, context, config)
predicates = evaluate(metrics, input_snapshot, context, config)
events, candidate_pending = detect(predicates, context, inbox)
plan = decide(context.phase, predicates, events, config)
outcomes = execute(plan, input_snapshot, context)
next_context, output = commit(context, candidates, plan, outcomes)
```

Это схема, а не обязательное число функций. Если метрики не нужны, соответствующий шаг отсутствует. Если нет очереди, `candidate_pending` не вводится. В коротком процессе нормализация и вычисление простых признаков могут быть рядом, если границы их смысла остаются видны.

Внутри диспетчера допустимы проверка технического результата вызова и передача аргументов. Предметная формула, политика допуска и правило восстановления должны иметь определённое место за его пределами. После чтения диспетчера можно ответить, **в каком порядке** работает процесс; после чтения селектора — **почему выбрано действие**.

### 10.2. Контракты важнее количества файлов

Для небольшой задачи весь пример помещается в одном модуле. При росте кода естественны четыре области:

| Область | Содержимое | Проверяется через |
|---|---|---|
| Модель | Типы входа, контекста, событий, плана и результата | Допустимые значения и инварианты |
| Политика | Предикаты, детекторы и выбор правила | Значения, границы и последовательности |
| Операции | Расчёты и адаптеры внешних действий | Их собственные контракты |
| Оркестрация | Порядок вызовов и фиксация | Связи, исходы и наблюдаемый результат |

Название файла вторично. Существенно, чтобы численная функция не меняла фазу через скрытую глобальную переменную, а селектор не обращался к сети при проверке guard.

Сложные операции удобно передавать как зависимость: `step(..., worker=calculate)`. В проверке на это место ставится небольшая функция с заранее известным исходом. В рабочем вызове используется настоящая операция. Интерфейс, базовый класс и контейнер зависимостей нужны только при реальной пользе для проекта.

### 10.3. Функции, switch или таблица

| Представление | Когда удобно | За чем следить |
|---|---|---|
| Обычные именованные функции | Несколько последовательных смысловых шагов | Не прятать изменение контекста в проверке |
| `if` / `switch` / `match` | Небольшое число хорошо различимых правил | Явный порядок приоритетов, короткие ветви |
| Таблица переходов | Много однотипных сочетаний состояния и события | Полнота применимых сочетаний, guards и исходы отказа |
| Иерархическая модель состояний | Есть повторяющееся поведение групп состояний | Понятная семантика входа, выхода и наследования правил |
| Общий движок правил | Несколько процессов действительно используют одинаковую механику | Стоимость расширения должна оправдывать дополнительный язык описания |

В схеме 3 filter2win тонкий диспетчер вызывает подготовку, расчёт условий и локального кандидата, чистый селектор, затем исполнитель с финальной публикацией. Селектор получает готовые признаки и возвращает `{event, action}`; он не рассчитывает модель и не меняет FIFO. Исполнитель принимает разрешённые изменения и определяет итоговый статус по фактическому результату. Для этой структуры не вводят DSL, реестр обработчиков или конфигурационный язык. Конкретный метод, границы параметров и смысл фазы и статуса описаны в [docs/filter2win_theory.md](../docs/filter2win_theory.md).

Если правило содержит сложное условие, таблица может ссылаться на именованный guard. Если в ячейке оказывается длинный фрагмент кода со скрытыми эффектами, таблица перестаёт быть обозримой спецификацией.

Один источник производственной политики полезен: правило реализовано в одном месте. Ожидаемые результаты тестов при этом должны иметь независимое смысловое основание. Эти два требования совместимы.

### 10.4. Где проходит граница ошибки

На внешней границе проверяются форма и допустимость входов. Внутри согласованного модуля можно опираться на его типы и предусловия; повторять всю валидацию в каждой функции не требуется.

Различаются:

- недопустимый пользовательский вход: предусмотренный ответ с причиной;
- ожидаемый отказ операции: предусмотренный неуспешный исход;
- неверная конфигурация: явная ошибка настройки;
- нарушение внутреннего контракта: ошибка программы, требующая диагностики.

Тихое приведение любого из этих случаев к «ничего не произошло» уничтожает информацию. В то же время исключение для обычного отсутствия нового пакета делает нормальный поток труднее читать.

## 11. Как проектировать содержательные тесты

### 11.1. Каждый тест проверяет обещание

Понятный тест состоит из трёх частей: заданные условия, одно существенное воздействие, наблюдаемое ожидание. В названии отражается правило: `failed_build_preserves_previous_report`, а не имя строки или внутренней ветки.

До запуска проверяющий должен понимать, почему ожидается именно такой результат. Хороший источник ожидания — требование, вручную рассчитанный простой пример, независимая спецификация или свойство, следующее из предметного смысла.

Неполезное ожидание выглядит так:

```text
actual = controller.step(input)
expected = production_selector(input)
assert actual.decision == expected
```

Так можно проверить связь контроллера с селектором, но нельзя установить правильность самого селектора. При общей ошибке обе стороны согласуются.

### 11.2. Разные границы — разные проверки

| Что проверяем | Что задаём | Что наблюдаем | Что такая проверка ещё не доказывает |
|---|---|---|---|
| Численную операцию | Небольшие данные с известным результатом | Значение, размерность, допуск, отказ | Правильность выбора момента запуска |
| Предикат | Значения ниже, на и выше границы | Истинность и причина | Жизненный цикл события |
| Детектор | Предыдущую память и последовательность наблюдений | События и кандидат памяти | Правильность арбитража |
| Селектор | Фазу, признаки, одновременные события | Правило, действия и исходы плана | Успех фактического исполнения |
| Исполнитель | План и управляемые результаты зависимостей | Порядок вызовов, статусы, блокировку зависимых действий | Корректность настоящего внешнего сервиса |
| Фиксацию | Старый контекст, план и исходы | Новые данные, фазу, подтверждение запроса | Корректность всех входных детекторов |
| Несколько сквозных сценариев | Последовательность реальных входов | Согласованное внешнее поведение | Все возможные истории и условия окружения |

Число тестов определяется различиями поведения. Не нужно писать отдельную проверку на каждую строку присваивания или повторять все комбинации на каждом уровне.

### 11.3. Набор, с которого удобно начать

Для конкретного правила выбираются применимые случаи:

1. Обычный допустимый вход.
2. Точная граница допуска и соседние значения.
3. Отсутствующий вход и отдельно недопустимый вход.
4. Два одновременно применимых события с известным приоритетом.
5. Ожидаемый отказ выбранного действия.
6. Сохранение ранее принятого результата после отказа.
7. Успешное восстановление после отказа.
8. Сброс и последующий новый цикл.
9. Повторное, отложенное или запоздалое событие, если такие события возможны.
10. Чередование работы двух контекстов, если процесс обслуживает несколько сущностей.

Это перечень рисков для выбора, а не требование механически создать десять тестов на любую функцию. Для одноразового чистого расчёта большая часть пунктов не нужна.

У численной проверки допуск задаётся из требований к точности и масштабу величин. Нельзя увеличивать его только ради прохождения падающего теста. Если результат должен быть приблизительным, сравнение точного двоичного представления обычно проверяет лишнее свойство.

### 11.4. Последовательности проверяют память

Одиночная строка таблицы не показывает, правильно ли обновляется история. Например:

```text
хорошие данные → плохие данные → нет новых данных → хорошие данные
```

Такой сценарий позволяет проверить сохранение результата, отсутствие ложного восстановления при молчании и принятие настоящего успешного обновления.

Для фронтов нужны последовательности `false → true → true → false`. Для счётчика — значения по обе стороны лимита. Для отмены — запоздалое завершение старого запуска после сброса. Ожидаемые результаты записываются для существенных шагов, а не только для последнего.

Если значимых историй становится много, можно генерировать последовательности действий и проверять инварианты. Инструменты вроде stateful testing в Hypothesis поддерживают такой подход.[3] Сам генератор не создаёт правильную предметную модель: условия действий и проверяемые свойства всё равно задаёт разработчик. Сначала обычно полезнее несколько понятных ручных сценариев.

### 11.5. Подменять именно нужную границу

Если проверяется реакция на отказ расчёта, достаточно передать функцию, которая сообщает предусмотренный отказ. Не нужно подбирать большой случайный набор данных в надежде вызвать его естественным образом.

Если проверяется запрет запуска, подмена может записывать вызовы или явно завершать тест при вызове. Если проверяется порядок зависимых операций, записывается последовательность их имён. Утверждения о числе вызовов нужны, когда это часть поведения: например, недопустимый пакет не должен запускать расчёт. Для внутренней функции без такого обещания проверка точного числа вызовов может лишь мешать рефакторингу.

Время, случайность и внешние ответы задаются управляемо. Для проверки таймаута достаточно двух значений времени. Реальная задержка `sleep` обычно проверяет планировщик окружения и замедляет обратную связь.

### 11.6. Условия воспроизводимости

Тест сам создаёт исходный контекст и не зависит от порядка запуска соседних тестов. Общий изменяемый объект в модуле тестов легко превращает локальную проверку в скрытую последовательность.

Для Python стандартный `unittest` предоставляет организацию отдельных тестов, фикстуры и проверки ожидаемых исключений.[2] В небольшом учебном файле допустимы обычные `assert`, если запуск выполняется без отключения утверждений. Выбор библиотеки не заменяет независимого ожидаемого результата.

## 12. Журнал и воспроизведение ошибки

### 12.1. Записывать объяснение решения

Если для задачи нужен диагностический след, из следующего списка выбираются достаточные поля. Статуса или возвращаемой причины может быть достаточно; отдельный журнал, версия правил, хеш и реестр результатов не обязательны.

| Поле | Для какого вопроса нужно |
|---|---|
| Идентификатор сущности и номер шага | Какой процесс рассматриваем? |
| Версия правил и конфигурации | По какой политике принято решение? |
| Исходная фаза и версия принятых данных | С какой памятью начали? |
| Существенные признаки и события | Что было известно? |
| Выбранное правило и причина подавления | Почему выбран этот вариант? |
| План и фактические исходы действий | Совпало ли намерение с исполнением? |
| Новая фаза и принятая версия | Что действительно изменилось? |
| Судьба входа или запроса | Принят, отложен, отклонён или отсутствовал? |

Не каждое поле нужно печатать при каждом вызове. Для маленького локального процесса идентификатор может определяться вызывающим кодом, а конфигурация фиксироваться один раз в начале сеанса. След должен позволять ответить на вопросы, ради которых он сохраняется.

Пример компактной записи:

```text
phase=OPEN; event=VALID_INPUT; action=BUILD; action_ok=false;
next=OPEN; last_attempt=FAILED; input=NOT_ACCEPTED; output=HELD;
reason=CALCULATION_FAILED
```

Видно, что построение было выбрано, выполнение не удалось, новый вход не принят, прежний результат сохранён. Одного сообщения «расчёт не выполнен» для этого недостаточно.

### 12.2. Воспроизведение требует входов

Для точного повторения решения нужны исходный контекст, последовательность входов и их порядок, существенные значения времени, конфигурация и версия логики. Если проверяется исполнение, понадобятся также ответы внешних зависимостей или возможность их воспроизвести.

Короткий журнал переходов удобен для диагностики, но сам по себе не восстанавливает отсутствующие данные. Сохранять полный вход или ссылку на его неизменяемую версию следует только там, где это действительно необходимо для расследования ошибок.

Хеш следа пригоден для быстрого сравнения или поиска различий. Совпадение хеша не доказывает равенство полного поведения: возможны коллизии, а не записанные в след поля вообще не участвуют в сравнении.

## 13. Отказы, восстановление и асинхронность

### 13.1. Удержание, восстановление и сброс

| Реакция | Что она означает | Какое условие нужно |
|---|---|---|
| Удержание | Ранее принятые данные остаются доступными с явным статусом | Политика разрешает их дальнейшую выдачу |
| Восстановление | Процесс снова удовлетворяет условиям нормальной работы | Положительное подтверждение пригодности или успешный результат |
| Сброс | Перечисленные данные и история очищаются | Явное событие или предусмотренное правило сброса |

После сброса недостаточно присвоить фазу готовности: должны существовать данные, которые обещает эта фаза. Отсутствие новой ошибки также не подтверждает восстановление, если в этот момент не было нового наблюдения.

Срок пригодности старого результата является отдельным требованием. Удержание не означает бессрочное разрешение считать результат актуальным. Если срок нужен, в контексте хранят время или версию и проверяют его явно.

### 13.2. Завершение асинхронной операции — новый вход

Для асинхронной работы решение обычно означает «разрешить запуск». Позднейший успех или отказ приходит отдельным событием. Контекст хранит идентификатор ожидаемого запуска и необходимые данные для сопоставления результата.

Типовой контракт:

```text
start(operation_id, generation, input_version)
complete(operation_id, generation, input_version, outcome)
```

При завершении проверяется, что результат относится к текущей ожидаемой операции. После отмены или сброса меняется поколение либо иным способом становится недействительным прежний идентификатор. Поздний ответ старой операции не заменяет данные нового цикла.

Простое сравнение со всеми изменениями общей версии контекста может оказаться слишком строгим: независимое обновление счётчика не обязательно делает расчёт устаревшим. Проверяются именно зависимости результата — активный запуск и версия его входных данных.

Если отмена и успех поступили одновременно, нужно определить значение слова «одновременно»: один входной снимок, одна партия сообщений или согласованный порядок номеров. Затем применяется заявленный приоритет. Реальная конкурентная реализация должна обеспечить такой порядок через владельца контекста или механизм синхронизации.

### 13.3. Повторение внешнего действия

Неизвестный исход внешнего вызова отличается от подтверждённого отказа. Если запрос мог быть выполнен, слепое повторение может создать второй эффект.

Для действия с такой особенностью контракт определяет идентификатор операции, способ проверки результата и допустимость повтора. Если доступна идемпотентность по ключу, повтор использует тот же ключ. Если доступна компенсация, у неё тоже есть собственный исход; она не является автоматическим стиранием истории.

Эти механизмы нужны для соответствующих внешних эффектов. Локальный чистый расчёт не требует очереди сообщений, распределённой транзакции или универсального менеджера повторов.

### 13.4. Общие ресурсы

Локальный контекст защищает независимость сущностей только в пределах правильно организованного владения. Общая очередь, реестр результатов или файл публикации остаются общей памятью.

Для каждого общего ресурса указывается, кто меняет его состояние и как упорядочиваются изменения. Масштабирование числа контекстов не исправляет гонку в общей точке записи. Если параллельного доступа нет, достаточно явно зафиксировать последовательную модель исполнения.
## 14. Полный пример с кодом и тестами

### 14.1. Задача и выбранные требования

Процесс получает пакет чисел и строит отчёт: количество элементов и среднее арифметическое. Он умеет закрывать приём, сбрасываться и сохранять прежний отчёт при неудачной новой попытке.

Это синхронный учебный процесс без внешних эффектов. Его правила полностью определены здесь:

| Область | Контракт |
|---|---|
| Один вызов | Один логический шаг с одним снимком `Request` и прежнего `Context` |
| Вход | `Request.batch` — кортеж чисел либо `None`; `reset` и `close` — булевы команды |
| Отсутствие | `None` означает отсутствие нового пакета; пустой кортеж означает поступивший непригодный пакет |
| Числа | Допускаются `int` и `float`, кроме `bool`; значения нормализуются в конечные `float` |
| Размер | Не меньше `min_size`; по умолчанию 2, граница включительна |
| Конфигурация | `min_size` — целое число не меньше 1; неверная настройка вызывает `ValueError` до обработки команд |
| Приём | Новый пакет считается принятым только после успешного построения и проверки результата |
| Отказ | Прежний принятый отчёт сохраняется; новая попытка получает отдельный статус |
| Закрытие | Запрещает построение по новым пакетам, сохраняя прежний отчёт |
| Сброс | Открывает приём, удаляет отчёт и очищает статус последней попытки |
| Конфликт | `RESET` имеет первый приоритет; при открытом приёме `CLOSE` имеет приоритет над пакетом |
| Подавленный пакет | Не ставится в очередь; получает `NOT_ACCEPTED` с причиной |

Вызов передаёт уже созданные `Request` и `Context`. При подключении JSON, файла или интерфейса внешнее представление преобразуется в эти типы на границе приложения. Проверки данного примера не являются универсальной схемой валидации произвольного сообщения.

### 14.2. Три независимых аспекта

**Управляющая фаза:** `OPEN` разрешает обработку новых пакетов, `CLOSED` запрещает её до сброса. Это две действительно разные политики реакции.

**Статус последней попытки:** `NONE`, `OK`, `REJECTED`, `FAILED`. Здесь попыткой называется обработка поступившего пакета, включая отказ до запуска вычисления. `REJECTED` означает недопуск; `FAILED` — выбранное вычисление не дало пригодного результата. Отсутствие нового пакета сохраняет этот статус. Сброс устанавливает `NONE`.

**Сохранённый отчёт:** существует независимо от исхода последней попытки. Поэтому возможен контекст с прежним отчётом и статусом `FAILED`. Ошибка нового расчёта не уничтожает успешную прошлую работу.

Статус выдачи относится к текущему шагу:

| Значение `output` | Смысл |
|---|---|
| `NONE` | Сохранённого отчёта нет |
| `CURRENT` | На этом шаге принят новый отчёт |
| `HELD` | Выдаётся ранее принятый отчёт |

`CURRENT` здесь не является обещанием свежести по времени. В примере нет срока годности данных; если он появится в требованиях, потребуется отдельная проверка возраста.

### 14.3. Таблица правил

Строки читаются сверху вниз. События формируются отдельно; отсутствие события представляется пустым множеством. Событие `VALID_INPUT` и действие `BUILD` имеют разные имена, поскольку пригодный пакет ещё не означает успешного построения.

| Фаза и условие | Действие | Фаза после шага | Последняя попытка | Отчёт |
|---|---|---|---|---|
| Любая; есть `RESET` | `CLEAR` | `OPEN` | `NONE` | Удалить |
| `CLOSED`; есть пакет, нет `RESET` | `REJECT_CLOSED` | `CLOSED` | `REJECTED` | Сохранить |
| `CLOSED`; нет пакета и `RESET` | `KEEP` | `CLOSED` | Сохранить | Сохранить |
| `OPEN`; есть `CLOSE` | `CLOSE` | `CLOSED` | `REJECTED`, если одновременно есть пакет; иначе сохранить | Сохранить |
| `OPEN`; непригодный пакет без более приоритетной команды | `REJECT` | `OPEN` | `REJECTED` | Сохранить |
| `OPEN`; пригодный пакет, расчёт успешен | `BUILD` | `OPEN` | `OK` | Принять новый |
| `OPEN`; пригодный пакет, ожидаемый отказ или непригодный выход | `BUILD` | `OPEN` | `FAILED` | Сохранить |
| `OPEN`; событий нет | `KEEP` | `OPEN` | Сохранить | Сохранить |

При одновременном сбросе и пакете статус последней попытки очищается, а возвращаемый след отдельно сообщает, что пакет не принят. При закрытии с пакетом фиксируется `REJECTED`. Такое различие выбрано явно.

У каждого допустимого события здесь есть определённая реакция в обеих фазах, включая отказ при закрытом приёме. Поэтому общий порядок событий не содержит неприменимого высокого события, которое могло бы бесконечно блокировать нижнее.

### 14.4. Что показывают функции

| Функция | Единственная основная обязанность |
|---|---|
| `normalize_input` | Привести допустимое представление чисел к общему виду |
| `evaluate_predicates` | Установить наличие и пригодность входа с причиной отказа |
| `detect_events` | Сформировать именованные события из запроса и признаков |
| `select_plan` | Выбрать действие и допустимую фазу по состоянию и событиям |
| `calculate_report` | Рассчитать кандидат отчёта |
| `execute_plan` | Выполнить выбранное действие и проверить контракт его результата |
| `commit` | Принять разрешённые изменения и объяснить исход шага |
| `step` | Вызвать перечисленные обязанности в определённом порядке |

В `Plan` достаточно трёх полей: события, действия и следующей фазы. Только локальные операции закрытия и очистки меняют фазу; в этом примере они не имеют ожидаемого отказа. Отказ расчёта оставляет фазу `OPEN` и изменяет статус попытки. Для процесса, у которого сама следующая фаза зависит от успеха операции, план должен описывать разные исходы, как в разделе 9.

`Outcome.ok` означает успешное исполнение **выбранного действия**. Успешно выполненный отказ `REJECT` имеет `ok=True`, но пакет остаётся непринятым. Принятие проверяется отдельно: выбрано `BUILD` и его исполнение успешно.

Встроенная численная функция использует `fsum`. Переполнение промежуточного суммирования считается предусмотренным отказом. Проверка выхода устанавливает тип результата, количество элементов и конечность среднего; правильность формулы подтверждается отдельными простыми ожиданиями в тестах. Проверка формы не способна установить, правильно ли произвольный подставленный вычислитель посчитал среднее.

Объявленный класс ожидаемых отказов вычислителя — `CalculationError`. Прочие исключения, включая программную ошибку рекурсии, не перехватываются как обычный неуспех. Для исключения без сообщения сохраняется причина `CALCULATION_FAILED`. Один тип обозначает общую границу ожидаемого отказа; отдельный тип для каждого численного условия не требуется.

from dataclasses import dataclass
from enum import Enum, auto
from math import fsum, isfinite


class CalculationError(RuntimeError):
    """Expected calculation failure; programming defects propagate."""


class Phase(Enum):
    OPEN = auto()
    CLOSED = auto()


class Attempt(Enum):
    NONE = auto()
    OK = auto()
    REJECTED = auto()
    FAILED = auto()


class Event(Enum):
    RESET = auto()
    CLOSE = auto()
    BAD_INPUT = auto()
    VALID_INPUT = auto()


@dataclass(frozen=True)
class Request:
    batch: tuple | None = None
    reset: bool = False
    close: bool = False


@dataclass(frozen=True)
class Report:
    count: int
    mean: float


@dataclass(frozen=True)
class Context:
    phase: Phase = Phase.OPEN
    report: Report | None = None
    last_attempt: Attempt = Attempt.NONE


@dataclass(frozen=True)
class Facts:
    has_input: bool
    can_build: bool
    values: tuple | None
    problem: str | None


@dataclass(frozen=True)
class Plan:
    event: Event | None
    action: str
    next_phase: Phase


@dataclass(frozen=True)
class Outcome:
    ok: bool
    report: Report | None = None
    problem: str | None = None


def normalize_input(request):
    if request.batch is None:
        return None, None
    if not isinstance(request.batch, tuple):
        return None, "BATCH_MUST_BE_TUPLE"
    if any(isinstance(x, bool) or not isinstance(x, (int, float))
           for x in request.batch):
        return None, "NON_NUMERIC_VALUE"
    try:
        return tuple(float(x) for x in request.batch), None
    except OverflowError:
        return None, "NUMBER_OUT_OF_RANGE"


def evaluate_predicates(request, values, problem, min_size):
    if type(min_size) is not int or min_size < 1:
        raise ValueError("min_size must be an integer >= 1")
    if request.batch is None:
        return Facts(False, False, None, None)
    if problem is None:
        if not all(isfinite(x) for x in values):
            problem = "NON_FINITE_VALUE"
        elif len(values) < min_size:
            problem = "TOO_FEW_VALUES"
    return Facts(True, problem is None, values, problem)


def detect_events(request, facts):
    return {event for event, active in (
        (Event.RESET, request.reset), (Event.CLOSE, request.close),
        (Event.BAD_INPUT, facts.has_input and not facts.can_build),
        (Event.VALID_INPUT, facts.can_build)) if active}


def select_plan(phase, events):
    priority = (Event.RESET, Event.CLOSE, Event.BAD_INPUT, Event.VALID_INPUT)
    event = next((item for item in priority if item in events), None)
    if event is Event.RESET:
        return Plan(event, "CLEAR", Phase.OPEN)
    if phase is Phase.CLOSED:
        has_input = bool(events & {Event.BAD_INPUT, Event.VALID_INPUT})
        return Plan(event, "REJECT_CLOSED" if has_input else "KEEP", phase)
    if event is Event.CLOSE:
        return Plan(event, "CLOSE", Phase.CLOSED)
    if event is Event.BAD_INPUT:
        return Plan(event, "REJECT", Phase.OPEN)
    if event is Event.VALID_INPUT:
        return Plan(event, "BUILD", Phase.OPEN)
    return Plan(None, "KEEP", phase)


def calculate_report(values):
    try:
        return Report(len(values), fsum(values) / len(values))
    except OverflowError as exc:
        raise CalculationError("NUMERIC_OVERFLOW") from exc


def execute_plan(plan, facts, worker):
    if plan.action == "REJECT":
        return Outcome(True, problem=facts.problem)
    if plan.action == "REJECT_CLOSED":
        return Outcome(True, problem="CLOSED")
    if plan.action in ("CLEAR", "CLOSE", "KEEP"):
        return Outcome(True)
    if plan.action != "BUILD":
        raise ValueError("Unknown action")
    try:
        result = worker(facts.values)
        if (not isinstance(result, Report) or type(result.count) is not int
                or result.count != len(facts.values)
                or type(result.mean) is not float or not isfinite(result.mean)):
            raise CalculationError("INVALID_RESULT")
        return Outcome(True, result)
    except CalculationError as exc:
        return Outcome(False, problem=str(exc) or "CALCULATION_FAILED")


def commit(context, request, plan, outcome):
    accepted = plan.action == "BUILD" and outcome.ok
    report = outcome.report if accepted else context.report
    attempt = context.last_attempt
    if plan.action == "CLEAR":
        report, attempt = None, Attempt.NONE
    elif plan.action == "BUILD":
        attempt = Attempt.OK if outcome.ok else Attempt.FAILED
    elif plan.action in ("REJECT", "REJECT_CLOSED"):
        attempt = Attempt.REJECTED
    elif plan.action == "CLOSE" and request.batch is not None:
        attempt = Attempt.REJECTED
    output = "NONE" if report is None else "CURRENT" if accepted else "HELD"
    disposition = "ABSENT" if request.batch is None else (
        "ACCEPTED" if accepted else "NOT_ACCEPTED")
    event_name = plan.event.name if plan.event is not None else "NONE"
    reason = outcome.problem or (event_name if disposition == "NOT_ACCEPTED" else None)
    trace = dict(old=context.phase.name, event=event_name, action=plan.action,
                 action_ok=outcome.ok, new=plan.next_phase.name,
                 last_attempt=attempt.name, output=output,
                 input=disposition, reason=reason)
    return Context(plan.next_phase, report, attempt), trace


def step(context, request, min_size=2, worker=calculate_report):
    values, problem = normalize_input(request)
    facts = evaluate_predicates(request, values, problem, min_size)
    events = detect_events(request, facts)
    plan = select_plan(context.phase, events)
    outcome = execute_plan(plan, facts, worker)
    return commit(context, request, plan, outcome)


# Выполняется после реализации выше в том же файле.
# Каждый тест создаёт свои данные; порядок запуска тестов не имеет значения.
# Ожидания заданы требованиями и ручным расчётом, а не селектором реализации.


def forbidden_worker(values):
    raise AssertionError("Вычисление не должно выполняться")


def accepted_context():
    return Context(Phase.OPEN, Report(2, 1.0), Attempt.OK)


def test_absent_input():
    # T1. Отсутствие пакета не является ошибкой и не запускает вычисление.
    empty = Context()
    unchanged, trace = step(empty, Request(), worker=forbidden_worker)
    assert unchanged == empty and trace["output"] == "NONE"
    assert detect_events(Request(), Facts(False, False, None, None)) == set()


def test_minimum_size_and_zero():
    # T2. Нижняя граница включается в допуск; численный ноль допустим.
    rejected, _ = step(Context(), Request((1,)), min_size=2,
                       worker=forbidden_worker)
    assert rejected.last_attempt is Attempt.REJECTED and rejected.report is None
    ready, trace = step(Context(), Request((0, 2)), min_size=2)
    assert ready == Context(Phase.OPEN, Report(2, 1.0), Attempt.OK)
    assert trace["output"] == "CURRENT" and trace["input"] == "ACCEPTED"


def test_invalid_input_preserves_report():
    # T3. Недопустимый пакет сохраняет прошлый отчёт без нового вычисления.
    ready = accepted_context()
    for batch in ((), (float("nan"), 1), (float("inf"), 1), (True, 1), ("1", 2)):
        rejected, trace = step(ready, Request(batch), worker=forbidden_worker)
        assert rejected.phase is Phase.OPEN and rejected.last_attempt is Attempt.REJECTED
        assert rejected.report == Report(2, 1.0) and trace["input"] == "NOT_ACCEPTED"
        assert trace["output"] == "HELD"


def test_worker_failure_preserves_report():
    # T4. Ожидаемый отказ функции не заменяет принятый отчёт.
    def failed_worker(values):
        raise CalculationError("CALCULATION_FAILED")

    failed, trace = step(accepted_context(), Request((8, 10)), worker=failed_worker)
    assert failed == Context(Phase.OPEN, Report(2, 1.0), Attempt.FAILED)
    assert trace["action_ok"] is False and trace["reason"] == "CALCULATION_FAILED"


def test_invalid_result_preserves_report():
    # T5. Непригодный выход функции также не считается успехом.
    failed, trace = step(accepted_context(), Request((8, 10)),
                         worker=lambda values: Report(2, float("nan")))
    assert failed == Context(Phase.OPEN, Report(2, 1.0), Attempt.FAILED)
    assert trace["reason"] == "INVALID_RESULT"


def test_reset_priority():
    # T6. RESET имеет приоритет над CLOSE и пакетом; пакет явно не принимается.
    reset, trace = step(accepted_context(), Request((8, 10), reset=True, close=True),
                        worker=forbidden_worker)
    assert reset == Context() and trace["event"] == "RESET"
    assert trace["input"] == "NOT_ACCEPTED" and trace["reason"] == "RESET"


def test_close_and_reopen():
    # T7. Закрытие сохраняет отчёт; новые пакеты запрещены до RESET.
    ready = accepted_context()
    closed, _ = step(ready, Request(close=True), worker=forbidden_worker)
    assert closed == Context(Phase.CLOSED, Report(2, 1.0), Attempt.OK)
    still_closed, trace = step(closed, Request((8, 10)), worker=forbidden_worker)
    assert still_closed == Context(Phase.CLOSED, Report(2, 1.0), Attempt.REJECTED)
    assert trace["input"] == "NOT_ACCEPTED" and trace["reason"] == "CLOSED"
    closed_with_input, trace = step(ready, Request((8, 10), close=True),
                                   worker=forbidden_worker)
    assert closed_with_input == still_closed and trace["reason"] == "CLOSE"
    reopened, _ = step(still_closed, Request(reset=True), worker=forbidden_worker)
    assert reopened == Context()


def test_wait_and_recover():
    # T8. Ожидание не стирает отказ; успешный новый пакет обновляет отчёт и статус.
    def failed_worker(values):
        raise CalculationError("CALCULATION_FAILED")

    calls = []
    def recording_worker(values):
        calls.append(values)
        return calculate_report(values)

    failed, _ = step(accepted_context(), Request((8, 10)), worker=failed_worker)
    waiting, trace = step(failed, Request(), worker=forbidden_worker)
    assert waiting == Context(Phase.OPEN, Report(2, 1.0), Attempt.FAILED)
    assert trace["output"] == "HELD"
    recovered, trace = step(waiting, Request((8, 10)), worker=recording_worker)
    assert recovered == Context(Phase.OPEN, Report(2, 9.0), Attempt.OK)
    assert calls == [(8.0, 10.0)] and trace["output"] == "CURRENT"


def test_context_isolation():
    # T9. Чередование двух процессов и сброс одного не изменяют другой.
    a0, _ = step(Context(), Request((2, 4)))
    b0, _ = step(Context(), Request((10, 20)))
    a1, _ = step(a0, Request((4, 6)))
    b1, _ = step(b0, Request(reset=True), worker=forbidden_worker)
    assert a1 == Context(Phase.OPEN, Report(2, 5.0), Attempt.OK) and b1 == Context()
    assert a0.report == Report(2, 3.0) and b0.report == Report(2, 15.0)


def test_invalid_configuration():
    # T10. Ошибка конфигурации отличается от отклонения входных данных.
    try:
        step(Context(), Request((1, 2)), min_size=0, worker=forbidden_worker)
    except ValueError:
        pass
    else:
        raise AssertionError("Недопустимая конфигурация должна сообщаться явно")


def test_decision_without_execution():
    # T11. Решение проверяется непосредственно, без исполнителя и численной функции.
    plan = select_plan(Phase.OPEN, {Event.RESET, Event.CLOSE, Event.VALID_INPUT})
    assert plan == Plan(Event.RESET, "CLEAR", Phase.OPEN)
    plan = select_plan(Phase.CLOSED, {Event.VALID_INPUT})
    assert plan == Plan(Event.VALID_INPUT, "REJECT_CLOSED", Phase.CLOSED)


tests = (
    test_absent_input, test_minimum_size_and_zero, test_invalid_input_preserves_report,
    test_worker_failure_preserves_report, test_invalid_result_preserves_report,
    test_reset_priority, test_close_and_reopen, test_wait_and_recover,
    test_context_isolation, test_invalid_configuration, test_decision_without_execution,
)
for test in tests:
    test()
print(f"{len(tests)} requirement scenarios passed")

Ни один ожидаемый план не получается вызовом производственного селектора. Численные ожидания `1.0`, `5.0` и другие заданы простыми ручными расчётами. Запрет исполнения проверяется функцией, которая немедленно сообщает об ошибочном вызове.

Пример показывает архитектуру одного синхронного процесса. Он не реализует очередь, асинхронную отмену, долговременное хранение и гарантию доставки внешнего действия. Правила их добавления описаны в разделах 7 и 13; включать их в этот код без соответствующей задачи не требуется.

## 15. Как менять существующий код

### 15.1. Сначала восстановить фактическое поведение

Перед переносом ветвей в таблицу нужно выяснить, какие входы читаются, где меняется память, какие действия вызываются и какие значения выдаются потребителю. Особенно полезен один реальный сценарий с последовательностью нескольких шагов.

Временная карта может быть небольшой:

| Участок | Читает | Изменяет | Вызывает | Предметный смысл |
|---|---|---|---|---|
| Ветка допуска | Новый пакет и настройки | Иногда скрыто обновляет историю | Расчёт | Проверка возможности обновления |
| Ветка отказа | Ошибку действия | Флаг и иногда результат | Журнал | Сохранение либо потеря прежних данных |
| Ветка сброса | Команду | Несколько полей | Очистку | Завершение прежнего цикла |

Карта описывает найденный код. Сопоставление с требованиями показывает, что следует сохранить, а что является ошибкой. Существующее поведение не становится правильным только потому, что оно давно работает.

### 15.2. Менять по одной смысловой границе

Практичная последовательность:

1. Зафиксировать несколько важных наблюдаемых сценариев и известных ошибок.
2. Дать имена существенным условиям, сохранив их точную семантику.
3. Сделать явными входы и владельца контекста; убрать случайную зависимость от глобальной памяти.
4. Сделать выбор обозримым, сохранив действующие приоритеты; отдельный возвращаемый план выделять по необходимости.
5. Отделить выполнение и принятие результата, явно описав отказ.
6. При необходимости заменить обозримые однотипные правила таблицей.
7. Удалить дублирование после проверки эквивалентности или согласованного изменения поведения.

Необязательно делать всё за один раз. Если основная ошибка находится в фиксации после отказа, сначала исправляется это правило и добавляется проверка именно его.

Для рефакторинга полезно сравнить старую и новую реализации на одинаковых входах. Такое сравнение выявляет различия, но не решает, какая версия права. В спорном случае требуется требование или независимо обоснованный пример. Намеренно исправленную ошибку нельзя возвращать ради совпадения со старым следом.

### 15.3. Сохранять смысл при удалении повторов

Два похожих условия могут иметь разные единицы, границы или политику отсутствия данных. Перед объединением нужно сравнить их контракты.

Объединяется повтор одного правила. Разные правила остаются отдельными, даже если сегодня оба содержат одинаковое сравнение. Иначе будущая правка одного требования незаметно изменит другое.

При удалении большого фрагмента сохраняется связь: какой смысл перенесён, куда он перенесён и чем теперь проверяется. Сокращение текста не должно уничтожать исключения, граничные случаи и реакцию на отказ.

## 16. Шаблоны описания логики

Шаблоны необязательны. Не создавайте отдельную карточку, если условия, поведение и ожидание уже понятны из кода и теста. YAML ниже — иллюстрация записи, не формат исполняемых правил и не основание для нового реестра.

Шаблоны заполняются только значимыми для задачи полями. Пустые секции, формальные номера и объём ради объёма не улучшают контракт. Ниже используются нейтральные примеры; выбранные значения относятся к ним, а не ко всем проектам.

### 16.1. Карточка условия

```yaml
predicate: enough_items
meaning: Пакет содержит не меньше настроенного количества элементов
inputs:
  count: Целое неотрицательное число
  minimum: Целое число не меньше 1
rule: count >= minimum
missing_input: Проверка неприменима; пакет не поступил
invalid_config: Явная ошибка настройки
memory: Не требуется
examples:
  - count=1, minimum=2 -> false
  - count=2, minimum=2 -> true
  - count=3, minimum=2 -> true
```

Для детектора дополнительно указываются прежняя память, кандидат новой памяти, момент её принятия и поведение при отсутствии наблюдения. Для пороговой метрики добавляются единицы и допустимость нечисловых или бесконечных значений.

### 16.2. Карточка события

```yaml
event: RECOVERY_CONFIRMED
source: Детектор подтверждения пригодности
kind: Фронт false -> true
payload: Версия наблюдения, подтвердившего восстановление
if_not_selected: Сохранить как pending
before_execution: Повторно проверить актуальность версии и отсутствие активного запрета
consume_on: Принятие соответствующего перехода
clear_on: Сброс или утрата актуальности
```

Если событие является внешним запросом, вместо политики фронта указываются ответ вызывающему, допустимость повторения и идентификатор запроса при необходимости.

### 16.3. Карточка перехода

```yaml
rule_id: BUILD_FROM_VALID_INPUT
requirement: Новый пригодный пакет можно принять только после успешного расчёта
from: OPEN
event: VALID_INPUT
guard: Нет более приоритетного применимого запроса
priority: Ниже RESET и CLOSE
plan:
  - BUILD_REPORT
on_success:
  phase: OPEN
  result: Принять новый отчёт
  last_attempt: OK
  input: ACCEPTED
on_failure:
  phase: OPEN
  result: Сохранить прежний отчёт
  last_attempt: FAILED
  input: NOT_ACCEPTED
invariant: Отказ не заменяет ранее принятые данные
```

Если фаза не меняется, переход всё равно может принимать новый результат или менять другие поля контекста. Смена `enum` не является единственным значимым изменением системы.

### 16.4. Карточка действия

```yaml
action: BUILD_REPORT
input: Непустой пакет допустимых чисел
precondition: Пакет прошёл проверку по действующей конфигурации
output: Кандидат отчёта с количеством элементов и средним
success: Кандидат соответствует контракту результата
expected_failure: Предусмотренный отказ численной операции
context_changes: Отсутствуют; принятие выполняет commit
external_effects: Отсутствуют
dependencies: Нормализованный пакет текущего шага
```

Для внешнего действия вместо строки об отсутствии эффектов описываются сам эффект, подтверждение, неизвестный исход и правило повтора. Для цепочки указывается, каким следующим действиям нужен успешный результат этого действия.

### 16.5. Карточка теста

```yaml
test: failed_build_preserves_previous_report
requirement: Отказ нового расчёта сохраняет ранее принятый результат
given:
  phase: OPEN
  previous_report: count=2, mean=1.0
  input: [8, 10]
  worker: Сообщает CALCULATION_FAILED
when: Выполнен один шаг
expect:
  phase: OPEN
  report: count=2, mean=1.0
  last_attempt: FAILED
  input_disposition: NOT_ACCEPTED
  output_status: HELD
oracle: Явное требование сохранения; прежние значения заданы непосредственно
```

Такая карточка достаточна для написания понятного теста. Она не должна содержать алгоритм повторного вычисления ожидаемого плана через производственную таблицу.

## 17. Контракт для программирующего агента

Этот раздел можно передать агенту вместе с конкретной задачей и исходным кодом. Он задаёт проверяемые обязанности; дополнительные архитектурные слои вводятся только при необходимости.

### 17.1. Вход задачи

Агент должен определить:

- наблюдаемый результат работы и существенные ограничения;
- входы, их допустимость и значение отсутствия данных;
- сохраняемую между шагами память;
- известные требования, выбранные допущения и нерешённые противоречия;
- существующие интерфейсы и поведение, затрагиваемые изменением.

Неясность нельзя маскировать придуманной предметной политикой. Для обратимых технических решений агент выбирает простой вариант и кратко объясняет его. Для неопределённости, меняющей пользовательское поведение, фиксирует конкретный вопрос или явно согласованное допущение. Все доступные части задачи выполняет без искусственной остановки.

### 17.2. Обязательства проектирования

1. **Выразить правило.** Для существенной реакции указать условия, разрешённые действия, исход успеха и исход отказа.
2. **Определить память.** Для изменяемого поля указать владельца, значение отсутствия и правила обновления и сброса.
3. **Разделить аспекты состояния.** Управляющая фаза, статус последней попытки и пригодность результата получают собственный смысл. Не создавать фазу для каждой функции.
4. **Назвать условия.** Предметные пороги и вычисления вынести из диспетчера. Условия одного шага вычислять по согласованному снимку.
5. **Описать события.** Указать источник, повторение и судьбу события при конфликте. Не терять одноразовый запрос без предусмотренной реакции.
6. **Сделать выбор определённым.** Сначала проверить применимость, затем приоритет. Описать совпадения и отсутствие применимого правила.
7. **Сделать выбор обозримым.** Для одного действия достаточно кода события, команды или явного вызова. `Decision`/`ActionPlan` и отдельная функция фиксации нужны только если упрощают несколько действий, отказ или принятие результата. При необходимости выбор проверяется без дорогой операции.
8. **Учесть фактический исход.** Фиксация принимает данные и фазу согласно выполнению. Выбранное действие не считается автоматически успешным.

### 17.3. Обязательства реализации

- Диспетчер показывает порядок вызовов. Предметная политика имеет определённое место.
- Селектор и предикаты не изменяют исходный контекст и не скрывают внешние вызовы. Необходимая память детекторов возвращается явно.
- Численная операция возвращает собственный результат и ожидаемый отказ. Она не управляет жизненным циклом через глобальные поля.
- Неуспешная попытка не затирает пригодные данные, если требование предусматривает их сохранение.
- Неизвестный исход, отсутствие данных и подтверждённый отказ различаются, когда от этого зависит реакция.
- Простой `if`, небольшая таблица или функция допустимы. Универсальный движок, отдельный сервис или абстрактный базовый класс требуют практического основания.
- Повторы удаляются после проверки совпадения смысла. Существенные границы и исключения сохраняются.

### 17.4. Обязательства проверки

Агент выбирает минимальный содержательный набор проверок для внесённого поведения:

- ожидаемые результаты выводятся из требований или независимых примеров;
- проверяется существенная граница, а при наличии памяти — последовательность;
- отдельная проверка выбора без реального исполнения добавляется, если ловит существенный риск изменённой логики;
- предусмотренный отказ и правила принятия результата проверяются управляемым исходом операции;
- настоящая численная функция имеет собственную проверку, если её корректность затронута задачей;
- неизменяемость и изоляция контекстов проверяются, когда это часть архитектуры;
- существующие обязательные проверки проекта выполняются в применимом объёме.

Тест не создаётся только ради покрытия присваивания или повторения реализации. После достаточной проверки агент завершает задачу; новые прогоны нужны для конкретного оставшегося риска или обязательного требования проекта.

В libtr это относится к изменённому поведению вычислительного кода. Для правил проекта и преобразователей документов новые тесты и приёмочные проверки не вводятся. Способ запуска, возвращаемые статусы и показ графиков определяются действующими правилами проекта.

### 17.5. Что агент должен предъявить

Результат работы включает реализацию и краткое объяснение:

1. Какое поведение реализовано или исправлено.
2. Где находятся условия, выбор правила, исполнение и фиксация.
3. Какие исходы и конфликты учтены.
4. Какие содержательные проверки выполнены и что они подтверждают.
5. Какие ограничения или неразрешённые вопросы действительно остаются.

При рефакторинге агент отдельно отмечает намеренное изменение поведения. При редактировании документа сохраняет содержательные правила и показывает, куда перенесены удалённые повторы. Наличие файла с общими словами не считается выполненным контрактом.

## 18. Критерии готовности и границы доказательства

### 18.1. Практическая готовность

Работу можно считать готовой в согласованном объёме, когда проверяющий способен:

- пройти один обычный сценарий от входа до принятого результата;
- объяснить каждую используемую фазу и значимое поле памяти;
- найти правило конфликта событий;
- увидеть реакцию на отсутствие данных и предусмотренный отказ;
- при необходимости проверить выбор действия без запуска дорогой операции;
- отличить новый результат от сохранённого прежнего;
- повторить существенный тест и понять источник ожидания;
- объяснить причину действия по коду, возвращаемому статусу или, когда это нужно, диагностическому следу.

Для маленькой задачи часть ответов помещается в несколько функций и комментариев. Полный набор документов, диаграмм и отдельных модулей не является самостоятельной целью.

### 18.2. Что именно доказано проверкой

| Полученный результат | Корректный вывод | Слишком сильный вывод |
|---|---|---|
| Все ручные сценарии прошли | Проверенные обещания выполняются на этих случаях | Ошибок вообще нет |
| Все строки таблицы исполнены | Движок обработал перечисленные сочетания | Требования отражены правильно и все истории рассмотрены |
| Одинаковые входы дают одинаковый план | Для заданных входов и памяти выбор воспроизводим | Внешние конкурентные эффекты всегда одинаковы |
| Инвариант проверен на многих шагах | На проверенных траекториях нарушение не найдено | Инвариант формально доказан для всех состояний |
| Численный пример совпал с эталоном | Конкретный расчёт соответствует проверенному ожиданию | Все размеры входа и численные режимы корректны |
| Время одного прогона мало | Измеренный сценарий укладывается в этот результат | Выполнены все требования к нагрузке и задержке |

Формальное доказательство возможно только относительно определённой модели и предположений. Тестирование даёт свидетельства о выбранных свойствах. Ясная спецификация помогает выбрать эти свойства и честно обозначить границы результата.
