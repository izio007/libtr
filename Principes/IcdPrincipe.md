# LIBTR: заметки об обмене данными

Это исходные технические решения для будущей задачи обмена. Библиотека
и все профили пока не реализованы. Документ не требует создавать портал,
универсальный конвейер, граф требований или начинать новую работу.

## Смысл данных и совместимость

Для выбранного интерфейса должны быть понятны источник и потребитель,
тип, размер, единицы, диапазон, кодирование, качество и поведение при отказе.
Описание и код хранятся в Git. Конфигурация проверяется до её применения;
ошибка не оставляет частично активированный набор настроек.
Смысл параметра не должен зависеть от случайного положения байтов.
Отсутствующее значение не трактуется как достоверный ноль.

Protobuf/nanopb — предложенный вариант, не выбранная зависимость.
При его использовании номера удалённых полей резервируются; совместимость
проверяется при изменении типа, единиц, смысла и битовой раскладки.
Неизвестные допустимые поля пропускаются по правилам формата. Protobuf
не требует общего преобразования чисел в Big-Endian; оболочка задаётся отдельно.
Старые биты не сдвигаются. Для предложенного байтового профиля отдельное
битовое поле не пересекает границу байта; порядок, ширины и резерв заданы явно.
Подписки выбирают только уже поддерживаемые бинарником данные и обработчики.

## Достоверность и правило 3T

Каждый параметр передаётся с признаком достоверности. Исправный транспорт
не исправляет недостоверное измерение источника.
Для периодического параметра срок актуальности равен трём периодам из ПИВ.
Возраст не менее 3T означает таймаут; это принятое требование сохраняется.

| Событие | Поведение приёмника |
|---|---|
| Первого значения ещё нет | Параметр недостоверен |
| Новое корректное достоверное значение | Обновить значение, качество и время |
| Источник сообщил недостоверность | Снять достоверность, сохранить последнее достоверное значение |
| Повреждённый кадр или параметр отсутствует | Не обновлять значение и срок актуальности |
| Истекли 3T | Снять достоверность, сохранённое значение не выдавать за новое |
| Повторное или устаревшее сообщение | Не заменять новое состояние и не продлевать свежесть |

Состояние и время хранятся отдельно по параметру и источнику в явном контексте.
Контроль таймаута работает и без входящих кадров. Начальный вариант — монотонные
часы приёмника; защита от задержанных сообщений дополнительно учитывает
последовательность и сеанс источника. Реакция потребителя на недостоверность
задаётся его задачей. Для событий и команд нужны отдельные сроки и подтверждения:
если периода нет, правило 3T неприменимо.

## Реализация выбранного профиля

Прикладной код работает со значением и качеством, кодек — с представлением,
транспортный адаптер — с каналом. Периодичность задаёт вызывающее приложение.
Каналы имеют независимые контексты; ретрансляция выполняется явно.
Сначала проверяется всё сообщение, затем публикуется согласованная группа
параметров. Ошибка не оставляет частично обновлённую группу.

Для встроенного C99-профиля буферы и пределы задаются заранее, malloc запрещён.
Переполнение даёт явный отказ; диагностика не блокирует обмен и ограничена
по памяти. CRC не заменяет проверку семантики и защиту от подмены.
При реализации нужны проверки повреждённых сообщений, границы 3T,
повторов, переполнения и независимости каналов — в объёме выбранного профиля.

| Вариант транспорта | Что уточнить для конкретной задачи |
|---|---|
| Ethernet / UDP Multicast | Адреса, размеры, потери, повторы, перестановка, нагрузка |
| UART / RS-485 | Границы кадров, вариант CRC-16, длина, синхронизация, доступ к линии |
| I2C | Роли, адреса, размеры транзакций, восстановление после ошибки |

Первая платформа, участники, ПИВ, размеры, задержки, атомарные группы,
конкурентный доступ и требования защиты пока не выбраны. Эти данные нужны
при возобновлении ICD-задачи ([need_chief.md](../need_chief.md)). Портал, YAML-подписки, FastAPI,
Pydantic и Qt остаются прежними вариантами, не обязательным составом проекта.
