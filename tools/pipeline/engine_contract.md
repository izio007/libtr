# Исполнение pipeline

`engine.py` содержит последовательный Python runner и транспорт JSON Lines.
Используется стандартная библиотека Python. Математика и критерии пригодности
остаются в конкретных тестах.

## Отчёт

`Pipeline(root, config)` создаёт один
`runtime/pipeline_runs/<id>/report.json`. Он содержит конфигурацию,
состояние запуска и список этапов. Каждый этап хранит `id`, `status`,
длительность и непосредственно возвращённое `value`.

Перед запуском этапы имеют состояние `NOT_RUN`. Исполняемый этап получает
`RUNNING`; нормальное завершение с JSON-совместимым значением даёт `PASS`.
При исключении этап и pipeline получают `FAILED`, оставшиеся этапы остаются
`NOT_RUN`. Тип ошибки, сообщение и traceback записываются в этот же отчёт.
Отчёт обновляется атомарно. Отдельного хранилища результатов нет.

MATLAB-значение содержит число запущенных тестов, `job_id`, `report_path`
и фактически возвращённые серверные этапы с их метриками. Число проверок
не вычисляется по количеству `assert`. У полного unit-прохода оно берётся
из `metrics.total` серверного этапа `unit`.

## Транспорт

Запрос отправляется один раз. Повторяются только запросы состояния после
таймаута, в пределах общего срока. Неопределённость доставки `submit`
не вызывает повторный запуск. Истечение срока не выдаётся за отмену
задания и не останавливает общий MATLAB-host.

Серверные lifecycle-состояния и политика широкого MATLAB unit-прохода
сохраняются. Python останавливает последовательность suites при первом
отказе; серверный широкий проход собирает результаты отдельных unit-тестов.
Это разные уровни отчётности. Ссылки на серверное задание сохраняются
в `value`, поэтому его журнал доступен после отключения клиента.

Проверки: `tools/runner.sh matlab/tests/configs/pipeline_engine_runner.json`.
Они не требуют запущенного MATLAB и не подключаются к TCP endpoint.
