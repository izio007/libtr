# Движок исполнения pipeline

Нормативное основание: .clinerules, разделы 1–3 — общий движок,
приоритет стандартных средств, настройка Cygwin и учёт исполнения.
Этот контракт конкретизирует реализацию и checks, но не заменяет регламент.
Известные несоответствия MATLAB-исполнителя норме учитываются в need_work.md,
раздел PIPELINE-ENGINE; принятие нормы не означает завершения его переработки.

Область: последовательное исполнение зарегистрированных этапов, транспорт,
дедлайн, отчёт и отказ. Не содержит математики, настройки сценариев, экспорта
или правил приёмки продукта. Python standard library; Cygwin Python 3.12.

- engine.py: JSON Lines transport, единственный submit/poll, Pipeline.
- declarative_runner.py: строгая конфигурация и регистрация исполнителей.
- pipeline_client.py: совместимый CLI для существующих потребителей provenance.
- filter2win_package_runner.py: проверка идентичности автономного host и адаптер.
- MATLAB host: существующий последовательный исполнитель; его жизненный цикл
  не меняется данным рефакторингом.

Критерии до реализации, проверяются pipeline_engine_runner.json:
1. Каждый этап изначально NOT_RUN; только нормальный возврат даёт PASS.
2. Первый отказ останавливает исполнение, последующие этапы остаются NOT_RUN.
3. Отчёт содержит hash конфигурации и атомарно сохраняется между этапами.
4. Defect Snapshot с traceback и job id сохраняется без перезаписи;
   неизвестные expected/actual/RNG обозначаются null, не придумываются.
5. submit ровно один; timeout status можно повторить только внутри общего
   дедлайна. Неопределённость доставки submit не вызывает повторную отправку.
6. Дедлайн не выдаёт cancel за выполненную отмену. MATLAB кооперативен;
   job id сохраняется, сервер не уничтожается и новый процесс не создаётся.
7. Busy host отклоняется до submit для любого зарегистрированного MATLAB suite.
8. Успешный stdout — только агрегированная строка; подробности в JSON.

Не удаляются используемые реестры, provenance и трассируемость. Их импорт
не должен быть транзитивной зависимостью штатного движка исполнения.
Старые архивы не переписываются. Сетевой протокол совместим с текущим host.

## Сравнение результата и ожиданий

Утверждённый объём дальнейшего упрощения и критерии проверки:
proposals/pipeline_simplification_decision.md. Наличие этого решения не означает
готовности MATLAB-адаптера или дедупликации его артефактов.

Расчётный JSON сохраняется один раз по SHA-256; запись исполнения содержит
ссылку, конфигурацию и оценку, но не копию результата. Сравнение точное,
без округления; время/PID/job id исполнитель не включает в расчётный JSON.
Предыдущий результат — только база сравнения, не эталон правильности.
Опциональный expectations в JSON задаёт по имени этапа список проверок:
path (список ключей/индексов), kind=equal с value либо kind=range с min/max.
kind=delta задаёт min/max для actual - previous; без предыдущей базы отказ.
Ожидания проверяются каждый раз, даже если результат не изменился.
Отсутствующее поле, нечисловое/не finite значение для диапазона, нарушение
ожиданий — FAILED и Fail-Fast. Пустой набор — NOT_RUN оценки ожиданий,
не выдуманный PASS математики. Проверки самого handler остаются обязательными.
Последний результат обновляется только после успешного этапа; отказ сохраняется
для диагностики, но не становится новой базой. Изменение конфигурации не скрывает
разницу; её hash остаётся в каждой записи исполнения. Это не кэш исполнения.
Проверки: повтор без нового объекта, изменённые значения, изменённое ожидание
для прежнего результата, отсутствующая база/поле, fail-fast, конечные числа.
MATLAB-логи и произвольные файлы старого исполнителя этим не дедуплицируются.
